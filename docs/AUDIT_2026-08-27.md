# Audit de sécurité et de cohérence — 2026-08-27

Périmètre : les quatre dossiers `fseg/`, `fsi/`, `superadmin/` et `template/`.
Méthode : lecture des routes, filtres, contrôleurs, modèles, services, migrations,
vues, configuration et tests ; diff `template/` ↔ instances ; revue par sous-agents
des vues (échappement/XSS) et des migrations/modèles/entités.

## État de l'art

- `fseg/`, `fsi/`, `superadmin/` sont byte-identiques entre eux (copies d'instance).
- `template/` est le dépôt modèle, **plus avancé** : il porte `AdminExitGuardFilter`,
  `AdminDashboardService` (onboarding), `ResourceController::centralContentGuard`
  (la superadministration ne modifie pas le contenu éditorial) et la création du premier
  administrateur facultaire dans le formulaire de création de site. Les instances sont
  donc en retard par rapport au modèle (évolutions fonctionnelles, pas des anomalies).
- Isolation multi-sites : colonne partagée `site_id`, `SiteScopedModel::forSite()`
  (where `table.site_id`) et `attachActiveSiteId` (beforeInsert automatique). Aucun contenu
  n'est isolé par dossier, tout est dans `ub_shared`.
- `Config/View.php` n'active **pas** l'autoescape global : tout `<?= ... ?>` doit
  passer par `esc()`. La convention est bien respectée partout, sauf un point (voir ci-dessous).

## Constats

### S1 — [HAUTE] XSS réfléchie dans la page de connexion
`app/Views/auth/login.php:34` (identique dans les 4 dossiers) :

```php
<input ... value="<?= old('email') ?>" required>
```

`old()` restitue la saisie utilisateur (contenu renvoyé après un échec de formulaire)
**sans échappement**. C'est la seule sortie non échappée trouvée dans l'ensemble des vues.
Impact : injection d'attribut puis de balise au rechargement de `auth/login`. Corrigé :
`esc(old('email') ?? '', 'attr')`.

### S2 — [BASSE] Liens protocol-relative vers les sites facultaires
`app/Views/admin/central/dashboard.php:103-104` : `esc('//'.$firstHost,'attr')`.
Les `hostnames` sont administrés par un superadmin et échappés ; reste un risque de
contenu mixte (http) si l'hôte cible n'est pas en https alors que la CSP force le
passage en https (`app.forceGlobalSecureRequests`). Correctif : préfixer systématiquement
par `https://`.

### D1 — [BASSE] Pas de clé étrangère `site_id` sur les tables de contenu
`2026-08-04-040000_CreateSitesAndScopeContent` n'ajoute qu'une **index** (pas de FK) sur
`site_id` des 17 tables « site-owned » ; seules `user_sites` et `content_blocks`
portent `FOREIGN KEY ... ON DELETE CASCADE`. La suppression d'une faculté n'est possible
ni via l'interface (`deletionDisabled`) ni via une commande (`site:delete` absent), donc
les orphelins ne peuvent apparaître que par SQL manuel. Recommandé : une migration de
verrous FK sur les bases neuves (à orchestrer avec retrait des orphelins éventuels) — non
appliquée automatiquement pour ne pas bloquer les bases existantes contenant des écarts.

### D2 — Signalement vérifié : valeurs de groupe à l'accueil
`app/Views/home/index.php:360-366` accède à `$group['orientation']` / `$group['programmes']`.
Vérifié : `HomePageService::programmeGroups()` initialise toujours ces clés
(`Licence/Master/Doctorat`, liste vide par défaut) — aucun risque d'avertissement PHP 8.2.
`$group['duration']` exploite `?? ''`. RAS.

### D4 — [MOYENNE] `down()` de la migration `SiteScopeAlumniSlugUnique` écrasait tout rollback
`2026-08-24-100000_SiteScopeAlumniSlugUnique::down()` (identique dans les 4 dossiers)
recréait l'index unique **global** `alumni_profiles_slug_unique` sur `slug` seul. Dès que
la table contient des slugs identiques répartis sur plusieurs sites (état légal du schéma
courant : un `alumni-exemple` par faculté), tout rollback — et donc tout run de test avec
`DatabaseTestTrait` (regress+migrate à chaque setUp) — échouait sur
`Duplicate entry 'alumni-exemple' for key ...alumni_profiles_slug_unique`.
Mis en évidence par la suite (`Tests: 124, Errors: 14`, les 14 au même endroit).
Corrigé : `down()` ne recrée l'index global que s'il n'existe pas déjà **et** qu'aucun
doublon de `slug` n'est présent (requête `GROUP BY ... HAVING COUNT(*) > 1`), sinon il
laisse la table sans index unique global (comportement de non-op, cohérent avec le
`down()` à non-op de `041000`). Validation : rollback complet + re-migration OK, suite verte.

### D3 — Signalement vérifié : amorçage du paramètre héro
`2026-08-04-020000_EnsureHeroCarouselDefaults` insère `home.hero_overlay_opacity` avant
l'ajout de `site_id` ; sur base neuve la ligne reçoit `site_id = 1` via le DEFAULT de
l'ALTER suivant (`041000`). Le provisionnement (`FacultySiteProvisioningService`) ré-insère
le paramètre propre à chaque faculté — cohérent, aucun orphelin exploitable. RAS.

## Zones auditées et jugées correctes

- Requêtes : aucune concaténation utilisateur dans le SQL courant ; le SQL brut réside
  uniquement dans les migrations et le bootstrap des tests (identifiants quotés propres).
- Isolation : milliers d'opérations CRUD examinées — `ResourceController` (index/delete/
  restore/purge/update), `PostController`, `MessageController`, `FacultyProfileController`,
  `UserController` imposent `forSite()` avant toute lecture/écriture par id.
  `restore()`/`purge()` réutilisent le builder déjà scopé (aucun contournement).
- `UserController` : un non-superadmin ne peut pas cibler `superadmin`/`admin`,
  la création est forcée en groupe `editor` sur le site actif ; auto‑verrouillage et
  dernier-superadmin protégés (`wouldLockOutSelf`, `wouldRemoveLastSuperAdmin`).
- URL publiques : `site_public_url()` n'autorise que `http://`, `https://`, `mailto:`,
  `tel:`, `#` ; les autres valeurs sont préfixées par `site_url()` — neutralise tout
  schéma `javascript:` même pour les champs `cta_url` non validés par `isHttpUrl()`.
  `registration_url` est, lui, validé par `isHttpUrl()` + `valid_url_strict`.
- Fichiers : `MediaService` limite la taille (2 Mo), les extensions (jpg/jpeg/png/webp)
  et stocke sous `public/uploads/{slug}/` (protégé) ; suppression des images orphelines
  sur erreur.
- CSRF : protection « session », formulaires System par `csrf_field()`/`form_open()`;
  filtres Shield sur `/admin` ; pas de route POST exempte.
- Dates publication : `PostController` interdit `published` futur et programme les
  `scheduled` ; `PostVisibilityService::applyVisible` applique aussi `published_at <= now`
  sur `published` (défensif, cohérent).
- `.env` : mêmes clés dans les 4 dossiers ; bases partagées `ub_shared`/`ub_shared_test`
  ; `superadmin` = port 8103 + `centralAdminMode=true` + `siteSlug` vide ;
  `template` = 8082 avec hosts de dev ; ok (aucun secret saisi dans ce document).
